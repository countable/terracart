How floor designs work

Dragon Hood / terracart - cave level architecture, shared vs per-floor definitions, scalability check. Evidence: file:line references from src/ as read on 2026-10-05.
One sentence: every underground floor is the procedurally derived "negative mirror" of the tile above it (recursing up to the real-world surface), so no floor is hand-drawn; per-floor identity comes from a handful of depth-keyed branches in worldgen.js plus well-tabled content windows (roster, habitats, loot, floor passes). The content layer scales cleanly; the terrain-identity layer does not, because floors 1-5 each have a bespoke branch where a table row should be.

1. The pipeline: how a floor gets made

A cave tile is generated on demand by loadCaveTile (worldgen.js:8768) when the player first descends. It never loads stored map data; it derives everything from the level above, which derives from the surface, which derives from real OSM tiles. The core rule (worldgen.js:7914-7918): a walkable cell above becomes CAVE_FLOOR, everything else becomes CAVE_WALL, recursively up to depth 0.

  1. Recursion up: fetch the level above's generated layer only (geologyGrid/baseGrid/genObjects), never the live entry with player edits, so every player sees the same cave (worldgen.js:8780-8788). Depth ≥ 2 also re-reads the surface tile (worldgen.js:8790-8792).
  2. Terrain: undergroundTerrain(surface, aboveGrid, depth) (worldgen.js:8703) picks the rule per depth - see the table below.
  3. Spawn gate: floorSpawnWhy(surface) (worldgen.js:618) carries only the inherited hard reasons (SPAWN_WHY_ALL_FLOORS = FARMLAND|GOLF, worldgen.js:617) from immutable surface evidence, then re-derives farmland/golf from the surface paint.
  4. Stairs: every generated down-stair above becomes this floor's up-stair at the same world point; each gets a wandering down-stair seeded by cellHash ^ depth (worldgen.js:8822-8840). L1 deliberately breaks the stair chain (rope/elevator descends instead); depth ≥ 2 gets a guaranteed fallback shaft (worldgen.js:8843-8854).
  5. Landing pockets: a 3x3 floor pocket around each stair and (on L2) each L1 ground_hole fall-site (worldgen.js:8856-8869).
  6. Geology freeze: geologyGrid = grid.slice() is snapshotted before Underground.project carves its street-mirror overlay (depth ≤ 2), so carved streets never propagate to deeper floors (worldgen.js:8871-8875).
  7. Chest mirrors: POI chests above mirror down at the same GPS point (caveChestsFrom, worldgen.js:8195); rank rides down, tiers do not. Each level then re-seats its own quota pyramid (seedChestTiers(objects, {cave:true})) and prunes to 50 lowest-tier mirrors (capCaveChests, worldgen.js:8232).
  8. Torches, gems, authored areas: torches seat where the low-tier POIs above stood (caveTorchSites, worldgen.js:8269); quarry gem provenance stamps down one level (worldgen.js:8650-8688); authored CaveAreas (spring caves) claim ground on L1 only (cave_areas.js:15-21).
  9. Floor passes: the CAVE_PASSES table (worldgen.js:8445) scatters rocks, mushrooms, chasms, coins, X-marks, torches, barrels - each row on its own depth-salted stream, in table order.
  10. Freeze for the next level: the entry stores baseGrid/genObjects/genWildplants copies, so player digging above never rerolls the level below (worldgen.js:8909-8913).

4. Is the design scalable?

What scales well

  • Adding depth is free. Generation recurses with no max depth; ore, chest tiers, enemy windows, theme bands and hazard mechanics are formulas or banded tables that already extend to Infinity.
  • Adding content is a row. A new kind with a cave window, a new band in THEME_BANDS, a new CAVE_PASSES row, a new loot formula input - each follows the project's stated rule (kinds as table rows, groups as predicates).
  • Cost stays flat per floor. Nothing iterates "all floors"; each floor derives from one parent plus the surface, and caches are per-depth.
  • Determinism holds. Depth-salted streams and the generated-layer freeze mean new floors never reroll old ones.

What does not scale

  • Terrain identity is branch code. undergroundTerrain hard-codes depth 1/2/3/4; lava is a special case at depth 5 inside loadCaveTile; chest sources branch on depth 3. A sixth distinct floor type means another branch in a 9,000-line file, not a new row.
  • Visual variety caps at three looks. undergroundBiome is a ternary with cave/deep_stone/underdark (worldgen.js:8902); floors 4, 5, 6... all render as plain "cave".
  • Transport has a hard list. Elevators.FLOORS = [0,1,2,3]; every stop beyond 3 is another code change.
  • Authored areas are singletons. CaveAreas implements one geometry (spring) at one depth; the weighted table names three more ids (goblin_warrens, mushroom_cavern, gemstone_cavern) that have story panels (underground_stories.js:6-8) but no layout code.
  • Per-depth features are scattered. L1-only flags live in four modules (pressure_traps.js, CAVE_PASSES, cave_areas.js, underground.js) instead of one per-depth profile.

Verdict

Yes for depth, no for floor types. The architecture scales to arbitrarily deep dungeons cheaply, because identity is data-driven windows over one shared derivation. It does not scale to many distinct floor designs: each new look today costs a bespoke branch in undergroundTerrain/loadCaveTile plus a biome ternary plus scattered per-depth flags. The mirror design itself (floors as derivatives of real-world surface data) is the load-bearing strength - keep it; the branches are the debt.

If more floor types are ever wanted, the convergent refactor is a per-depth floor profile table - one row per depth owning: terrain rule, biome label, chest source, and feature flags - with the current branches becoming rows 1-5 and specials (lava, arena) becoming row properties. That matches the pattern the codebase already uses everywhere else (CAVE_PASSES, THEME_BANDS, roster windows). No such refactor is needed while floors 6+ staying visually plain is acceptable.
